# CHAPTER 7: CONCLUSION AND RECOMMENDATIONS

## 7.1 Introduction

This final chapter reviews the development of the National Railways of Zimbabwe (NRZ) Hardware Department Inventory System. The preceding chapters described the system design, implementation, testing evidence, and post-implementation plan. This chapter brings those findings together by summarizing the completed application, identifying the project achievements, acknowledging the current limitations and development challenges, and recommending the activities required for responsible organizational adoption and future growth.

The conclusion reflects the present state of the project. The system is a functional Laravel and FilamentPHP administrative application with authentication, permissions, asset records, maintenance logs, audits, gate passes, QR code generation, dashboard statistics, and saved reports. It remains a development and demonstration system until production configuration, approved data migration, user acceptance, operational backups, and formal deployment have been completed.

## 7.2 Summary of the Project

The project was undertaken to provide a centralized digital foundation for managing NRZ hardware inventory. The implemented application replaces the need to manage all inventory information through disconnected application screens, spreadsheets, and paper-based processes by providing structured database records for assets, departments, locations, users, maintenance work, audits, gate passes, and inventory reports. The current project includes Laravel 12, PHP 8.2 or later, FilamentPHP 5.7, Eloquent ORM, Spatie Laravel Permission, Simple QrCode, Tailwind CSS, Vite, and PHPUnit.

The system allows authorized users to register hardware using asset tags, serial numbers, hardware types, brands, technical specifications, purchase dates, warranty dates, departments, locations, assignment details, lifecycle status, and decommissioning information. It records maintenance work using pending, in-progress, and resolved statuses, stores audit results such as found, missing, damaged, and wrong location, and records the controlled collection of assets through gate passes. The dashboard and reports page calculate current database summaries for assets, warranties, maintenance, departments, and locations, while the QR code action creates a signed asset-information URL for an individual asset.

The project also provides a repeatable DatabaseSeeder containing demonstration permissions, roles, departments, locations, users, assets, maintenance records, audits, and a gate pass. The automated test suite currently verifies authentication, registration, email verification, password management, profile operations, account deletion, and the basic application response. These tests passed during verification, but dedicated automated tests for the inventory modules and formal user acceptance testing remain future activities.

## 7.3 Achievements of the Project

A significant achievement is the creation of a structured digital inventory model using Laravel migrations and Eloquent relationships. Assets can be associated with departments, locations, and assigned users, while maintenance logs and audits preserve operational history as related records. Gate passes and inventory reports are also linked to users and assets, creating a consistent data structure for future accountability. This provides a stronger foundation for inventory control than unstructured manual records, although the replacement of official NRZ records will only be complete after data migration and production adoption.

The project successfully implements role and permission management through Laravel authentication and Spatie Laravel Permission. The seeded roles are Administrator, Inventory Manager, Technician, Auditor, and Read Only, with permissions controlling access to assets, maintenance, users, reports, audits, and gate passes. This gives the system a practical authorization structure that can be reviewed and adjusted as NRZ responsibilities are confirmed.

The project also implements the main operational inventory workflows. Asset records support unique asset tags and serial numbers, department and location relationships, assignment information, active and decommissioned lifecycle states, and decommissioning reasons. Maintenance records preserve repair details and work progress, audit records capture physical verification results, and gate passes record asset collection, the collector, release time, issuing user, and related maintenance information. These features establish the core record-keeping capabilities required by the proposed inventory process.

The QR code functionality is another completed achievement. The asset table can generate a QR code dynamically using the Simple QrCode package. The code contains a signed asset-information URL and is displayed through a Filament modal. This supports a future physical labeling and identification process without claiming that a separate mobile scanner application has already been developed. The dashboard and reporting functions also provide useful summaries of current records, warranty dates, maintenance statuses, departments, locations, and saved report results.

Finally, the project established a maintainable development structure. The application separates models, migrations, Filament resources, pages, widgets, forms, tables, seeders, and tests. The existing automated suite passed with 25 tests and 61 assertions during verification, demonstrating that the authentication and profile foundations operate under the configured test conditions. This is valuable evidence of software quality, while also showing where inventory-specific test coverage must be expanded.

## 7.4 Challenges Encountered

One challenge is the difference between the data required by the new system and the data that may exist in historical NRZ records. Existing paper registers and spreadsheets may use inconsistent asset names, incomplete serial numbers, different department labels, or missing location and assignment information. This makes data cleansing, duplicate detection, and manual verification necessary before the application can become the official inventory source.

A second challenge concerns relational integrity. The system requires asset tags and serial numbers to be unique and requires assets to be linked to valid departments and locations. At the same time, assets may be reassigned to different users or organizational units over time. The current design stores the current assignment directly on the asset and preserves maintenance and audit history in related records. Future requirements for complete assignment history may require an additional asset movement or assignment-history design rather than simply changing the current assignment fields.

Environment configuration also requires careful management. QR codes are generated from signed asset-information URLs, so the application URL and QR base URL must be correct for the network where the code will be used. The local environment currently supports development through Laravel's Artisan server and uses environment configuration that can default to SQLite, while a production installation may use MySQL and a different domain or LAN address. Incorrect environment values could make a QR link inaccessible even when the code itself has been generated correctly.

Testing coverage remains a further challenge. The existing PHPUnit suite provides useful coverage for authentication and profile behavior, but it does not yet test the complete asset, maintenance, audit, gate pass, report, QR, and role-permission workflows. The project therefore cannot claim that every inventory process has passed formal automated testing or user acceptance testing. Expanding these tests will require realistic model factories or test records, authorization scenarios for each role, relationship assertions, validation checks, and test database setup.

The project also has a defined boundary between implemented and planned functionality. It currently does not provide CSV import, document uploads, Excel report exports, automated notifications, universal activity logging, a dedicated mobile scanner application, production backup automation, or external procurement and employee-system integrations. PDF report downloads are available from the Reports page. Managing this boundary has been important in keeping the documentation accurate and in preventing proposed future features from being presented as completed system capabilities.

## 7.5 Recommendations

The system should be introduced through a controlled pilot rather than being declared the official inventory source immediately. NRZ management and IT administrators should select the pilot location and participating departments, prepare the production environment, migrate a verified sample of records, and run the core workflows with authorized users. A short parallel period with existing records may be used where necessary, but it should have a defined reconciliation process and end date before the digital system becomes the authoritative record.

Role-based training should be completed before production use. Administrators, Inventory Managers, Technicians, Auditors, and Read Only users should practise only the functions allowed by their permissions. Training should use a separate demonstration or training database, and the final user manual should use screenshots and labels from the approved deployment environment. The current QR action should be demonstrated as implemented, while mobile scanning should not be included in training until a dedicated scanning workflow has been developed and tested.

The IT administration team should establish backups, restoration testing, access reviews, and update procedures before go-live. The project does not currently contain automated backup scripts, so the organization should define its own approved backup frequency, retention period, encryption method, off-site storage arrangement, and recovery responsibilities. Production updates to PHP, Laravel, FilamentPHP, Composer packages, Node.js packages, and frontend dependencies should be tested before release and recorded in a change history.

Regular physical audits should be scheduled using the implemented audit module. Audits should compare the physical asset, asset tag, serial number, department, location, assigned user, and condition with the database record. Differences should be documented and corrected through an approved process rather than being silently overwritten. This practice will improve data quality and provide management with a recurring measure of inventory accuracy.

The automated test suite should be expanded before the system is considered production-ready. Recommended tests include asset creation and uniqueness validation, department and location relationships, maintenance status transitions, audit result validation, gate pass associations, report summary calculations, QR URL generation, and permission restrictions for all seeded roles. After these tests are added, formal user acceptance testing should be carried out with representative NRZ users using realistic registration, maintenance, audit, gate pass, QR, and reporting scenarios.

## 7.6 Future Enhancements

A mobile-friendly scanner workflow is a major future enhancement. The current system generates QR codes and signed asset-information links, but it does not provide a dedicated scanner application or a complete mobile asset-verification process. A future implementation could provide a mobile-optimized page for scanning or entering an asset identifier, viewing the relevant record, recording audit results, and submitting maintenance information. It should be tested for authentication, network availability, authorization, and usability before being introduced into workshop or storeroom operations.

The reporting module could be extended with PDF and Microsoft Excel exports, scheduled reports, and additional analytical views. Possible additions include warranty-expiry lists, department allocation summaries, maintenance turnaround measures, missing or damaged asset reports, and historical asset movement reports. Any export feature should respect user permissions and protect sensitive information.

Automated notifications could improve operational response. Future notifications may alert authorized users about warranties approaching expiry, maintenance records that remain unresolved, completed repairs awaiting collection, or assets requiring audit follow-up. These notifications would require approved email or in-application notification channels, configurable recipients, and tests to prevent duplicate or misleading alerts.

The current assignment fields record the latest assigned user, date, and notes. A future asset movement history module could record every transfer between users, departments, and locations without losing previous assignments. This would strengthen accountability and support historical reporting. Related future integrations could connect the inventory system to approved procurement, human-resources, identity, or finance systems, but such integrations should be introduced only after their data ownership, security, and interface requirements have been agreed.

Other future improvements include a controlled CSV import process, document attachments for receipts and warranty evidence, automated database backups, activity logging for administrative events, improved dashboard filtering, and expanded performance monitoring. Each enhancement should be prioritized according to NRZ operational value, security risk, implementation effort, and available infrastructure.

## 7.7 Conclusion

The NRZ Hardware Department Inventory System has established a practical digital foundation for managing assets, maintenance activities, audits, gate passes, QR identification, and inventory reports. Its Laravel and FilamentPHP architecture provides a maintainable administrative interface, while Eloquent relationships and database constraints support consistent asset records. Authentication and permission controls provide the basis for separating administrative, inventory, maintenance, audit, and read-only responsibilities.

The project has achieved its implementation objectives at development and demonstration level, and its automated authentication and profile tests provide verified evidence for part of the application. However, it should not yet be described as a fully deployed organizational solution. Production data migration, formal inventory-module testing, user acceptance, backup and recovery controls, training, and infrastructure approval remain necessary steps before operational adoption.

With the recommendations and future enhancements described in this chapter, the system can develop from its current administrative inventory foundation into a broader NRZ asset-control service. Its long-term value will depend on disciplined data governance, regular physical audits, secure maintenance practices, responsive user support, and continued development guided by the actual needs of the Hardware Department.
