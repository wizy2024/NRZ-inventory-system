# CHAPTER 4: SYSTEM DESIGN

## 4.1 Introduction

The system design phase bridges the gap between the requirements identified during analysis and the implemented software. For the National Railways of Zimbabwe (NRZ) Hardware Department inventory system, this chapter describes the technical design of the Laravel web application and its FilamentPHP administrative panel. The design explains how users enter and retrieve information, how asset and maintenance processes are represented, how the relational database is organized, how QR codes are produced, and how access to administrative functions is controlled. The design reflects the current implementation of the system, which provides a centralized platform for recording NRZ hardware, associating assets with departments and locations, monitoring maintenance work, recording audits, issuing gate passes, and preparing inventory reports.

## 4.2 Input Design

Input design defines how users submit accurate and complete information to the system. The NRZ Inventory System uses FilamentPHP forms for the creation and maintenance of records in the administrative panel. The asset form captures the asset tag, serial number, optional MAC address, asset type, brand, technical specifications, purchase date, warranty expiry date, department, location or station, assignment information, status, and decommissioning details. Asset tags and serial numbers are unique database values, while required form fields and server-side validation prevent incomplete records from being saved. Asset types are selected from controlled options such as Desktop, Laptop, Server, Printer, Network Device, and Other.

The system also provides forms for the operational records that support inventory control. Maintenance users can select an active asset, identify the technician, describe the reported symptom, enter a detailed description, and assign a work status of pending, in progress, or resolved. Resolution date and resolution notes are displayed when a maintenance record is marked as resolved. Audit forms allow an authorized user to select an asset, record whether it was found, missing, damaged, or in the wrong location, identify the person who performed the check, and capture the date and audit notes. Gate pass forms record the asset being collected, the related maintenance record where applicable, the collector's name and contact details, an identification or employee number, the release date and time, the issuing user, and any handover notes.

The current implementation uses the asset tag and serial number as the primary means of identifying hardware in the administrative interface. It provides a QR code action for each asset, but it does not currently implement direct barcode-scanner input or an independent scanner workflow. A scanner that behaves like a keyboard could still supply an identifier to a compatible search field, but such a workflow is not a separate implemented feature of the application.

## 4.3 Output Design

Output design describes how the system presents processed information to administrators and inventory personnel. The main output is the FilamentPHP dashboard, which displays live statistics derived from the database. These statistics include the total number of registered devices, active devices, assets with warranties expiring within thirty days, open maintenance records, decommissioned assets, NRZ locations, and departments represented in the inventory. The dashboard values are linked to relevant inventory views so that users can move from a summary value to the records supporting it.

The asset table presents searchable and sortable information including the asset tag, serial number, MAC address, type, brand, purchase date, warranty expiry, department, location, assigned user, status, and decommissioning date. Each asset also has a QR code action. When the action is selected, the application generates a signed asset-information URL and renders a QR code in a modal window. This means that the QR code is generated when it is requested rather than being managed as a permanently uploaded image file.

The Reports page provides operational summaries and a PDF download. Users with the required permission can view asset distributions by type, department, and location, maintenance counts grouped by status, expired and soon-to-expire warranties, and recently saved reports. The system supports the creation of inventory summary, maintenance, and warranty reports. Each saved report contains a title, report type, generated summary values, optional notes, the user who generated it, and the generation date and time. Excel, depreciation, and missing-item export functions are not part of the current implementation and should be treated as possible future enhancements rather than existing outputs.

## 4.4 Process Design

Process design explains how the application transforms submitted data into operational records and visible results. The central process is the hardware lifecycle, beginning when an administrator registers an asset. At registration, the asset receives a unique asset tag and serial number, is linked to a department and location, and normally receives an active status. The record may also be associated with a user, an assignment date, and assignment notes. An asset can later be marked as decommissioned with a reason and date when it is removed from service.

Maintenance is represented as a related workflow rather than as an automatic change to the asset status. A maintenance record can only be created for an active asset and records the reported problem, the responsible technician, and the progress of the work. Its status moves from pending to in progress and finally to resolved when the repair is completed. The resolved state makes it possible to record the resolution date and resolution notes and allows a resolved maintenance record to be associated with a gate pass. The application therefore preserves the maintenance history of an asset while keeping the asset's own lifecycle status separate.

The gate pass process records the controlled release or collection of an asset. The system generates a unique gate pass number, identifies the asset and, when appropriate, the resolved maintenance record, and records the person collecting the machine, the relevant contact or identification details, the release time, the issuing user, and handover notes. Audits provide a separate verification process in which the recorded condition and location of an asset can be compared with its physical state. These records support accountability, but the current implementation does not automatically create an audit entry for every ordinary user interaction.

## 4.5 Database Design

The system uses a normalized MySQL relational database accessed through Laravel's Eloquent ORM and database migrations. The users table stores authenticated user accounts, while the Spatie permission tables support roles and individual permissions. The departments and locations tables store the organizational units and stations used to classify assets. The assets table is the central inventory table and stores unique asset identifiers, hardware details, specifications in JSON format, purchase and warranty dates, department and location foreign keys, assignment fields, status, and decommissioning information.

The relationships are represented with foreign keys and Eloquent relationships. Each asset belongs to one department and one location and may be assigned to one user. An asset can have many maintenance logs and many audit records. Each maintenance log belongs to one asset and may identify a technician. A gate pass belongs to an asset and may reference a maintenance log and the user who issued it. Inventory reports belong to the user who generated them and store their calculated summary as structured JSON data. This design does not use a separate asset-assignment pivot table; the current assignment is stored directly on the asset through the assigned user, assigned date, and assignment notes fields.

The database structure also separates current state from historical operational records. The asset status indicates whether a device is active or decommissioned, while maintenance status records the progress of repair work and audit results record the outcome of physical verification. This separation allows the system to retain maintenance, gate pass, audit, and reporting information without overwriting the core identity of the asset.

## 4.6 File and Generated Data Design

File design describes how the application handles files and generated data that are not ordinary relational fields. In the current implementation, asset specifications and saved report summaries are stored as structured JSON values in the database. The QR code displayed for an asset is generated dynamically by the QR code package and rendered in the Filament interface using a signed URL. It is not currently saved as a user-uploaded image or managed through a public file disk.

The implemented system does not currently provide upload fields for asset photographs, purchase receipts, or warranty documents. Consequently, there is no active private-document storage workflow or authenticated download controller for these files. Laravel's storage facilities could support those functions in a future extension, but documenting them as existing behavior would not accurately describe the present system.

## 4.7 User Interface Design

The user interface is implemented through the FilamentPHP administrative panel and styled using the project's Tailwind CSS setup. The panel groups the main functions into recognizable areas for inventory, maintenance, audits, gate passes, users and roles, and management reports. Tables provide searchable columns, sorting, filtering, record actions, and bulk actions where appropriate. Forms use relationship selectors for departments, locations, users, assets, and maintenance records so that users select existing records instead of manually entering foreign-key values.

The interface is designed for administrative use and presents the information in responsive Filament tables, forms, dashboard statistics, and modal actions. The asset table exposes the most important identification and allocation details, while the maintenance and audit screens provide focused workflows for repair tracking and physical verification. The QR code action is available directly from the asset table, reducing the number of steps required to identify an asset or prepare its label. The current design is responsive at the framework level, although the primary workflows are centered on the Filament web panel rather than on a separate native mobile application.

## 4.8 System Controls Design

System controls protect the confidentiality, integrity, and availability of inventory information. Authentication is provided through Laravel's user system, and user passwords are stored using Laravel's hashed password cast. The User model uses Spatie's role and permission functionality, allowing access to be assigned through roles as well as through additional individual permissions. Resource and page access is checked through permissions such as managing users, managing maintenance, and viewing reports. These checks restrict sensitive actions according to the user's authorization rather than relying only on the visibility of a navigation item.

Data integrity is supported by database uniqueness constraints and form validation. Asset tags, serial numbers, and optional MAC addresses are unique where supplied, while required relationships ensure that an asset has a department and location. Gate pass numbers are generated and validated as unique. The forms restrict status and result fields to controlled values, and dependent fields such as maintenance resolution details are shown when the selected workflow state requires them. These controls reduce duplicate records, invalid relationships, and incomplete operational entries.

Accountability is supported through explicit user references on reports, audits, maintenance records, and gate passes. The system therefore records who generated a report, who performed an audit, who was assigned to maintenance, and who issued a gate pass. This should be distinguished from a universal automatic activity log: the current application records accountability on these domain records but does not silently record every create, update, view, or delete action in a separate activity-log table.

## 4.9 UML Diagrams

UML diagrams provide a standardized way to describe the structure and behavior of the NRZ Inventory System. The use case diagram should show the system boundary containing asset management, department and location management, maintenance management, audit recording, gate pass recording, QR code viewing, user and role administration, and report generation. The actors and permissions should be presented according to the implemented responsibilities. An administrator or authorized inventory manager can manage users and roles where permitted, register and update assets, maintain department and location records, view QR codes, record audits, manage gate passes, and create reports. A maintenance user with the relevant permission can create and update maintenance records. A report user with the view-reports permission can access the Reports page and its inventory, maintenance, and warranty summaries.

The class or entity relationship diagram should show User, Asset, Department, Location, MaintenanceLog, GatePass, Audit, and InventoryReport as the principal entities. User has many assigned assets, audits, gate passes issued, maintenance records where applicable, and generated reports. Asset belongs to a department and location, may belong to an assigned user, and has many maintenance logs and audits. GatePass belongs to an asset and may reference a maintenance log, while InventoryReport belongs to its generating user. The diagram should show these relationships directly rather than introducing an Asset_Assignments entity that is not present in the current database design.

In the final physical document, the use case diagram and entity relationship or class diagram should be inserted as figures. Their purpose is to make the system boundary, authorization rules, data ownership, and operational relationships visible to the reader. The narrative descriptions in this section provide the basis for producing those figures from the implemented application.

## 4.10 Chapter Summary

This chapter described the design of the NRZ Hardware Department inventory system as implemented with Laravel, FilamentPHP, Eloquent, MySQL, Tailwind CSS, and Spatie roles and permissions. It explained the forms used to capture asset, maintenance, audit, gate pass, user, and report data, as well as the dashboard and reports used to present inventory information. The chapter also clarified the distinction between asset lifecycle status and maintenance workflow status, described the direct assignment fields used by the current database, and documented the dynamic QR code process.

The design provides a structured foundation for inventory accountability by linking assets to departments, locations, users, maintenance records, audits, gate passes, and saved reports. It also identifies the boundaries of the present implementation: barcode scanning, document uploads, Excel exports, and universal automatic activity logging are not currently included. These documented design decisions provide an accurate technical basis for the implementation, testing, and evaluation discussed in Chapter 5.
