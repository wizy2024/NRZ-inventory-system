# CHAPTER 5: CODING AND TESTING

## 5.1 Introduction

The coding and testing phase translated the design decisions described in Chapter 4 into an operational NRZ Inventory System. The application was implemented as a Laravel web application with a FilamentPHP administrative panel. This chapter describes the actual development environment, programming technologies, implemented modules, available test data, automated tests, and the current evidence from system verification. It also distinguishes between functionality that is implemented and functionality that still requires additional testing or development, ensuring that the chapter accurately represents the present state of the system.

## 5.2 Development Environment: Software and Hardware Used

The application was developed in a Windows workstation environment using Visual Studio Code as the main integrated development environment. The repository is managed as a Laravel project and includes the Composer dependencies, Node.js build configuration, database migrations, seeders, application source code, and automated tests required for development. The project can be run locally through Laravel's Artisan development server, while Vite provides the frontend asset development and build process.

The software requirements defined by the project include PHP version 8.2 or later, Composer for PHP dependency management, Node.js and npm for frontend dependencies, and a MySQL-compatible relational database. The application is configured through Laravel environment variables, including database connection details and the application URL. The repository also includes Laravel Sail as a development dependency, but the project files do not establish that XAMPP was used as the active development server. Therefore, XAMPP, GitHub hosting, and a specific workstation specification such as 8GB of RAM should only be stated as part of the development environment if they are separately confirmed by the project records.

Visual Studio Code was used to edit PHP, Blade, JavaScript, CSS, migration, and configuration files. Composer manages Laravel 12, FilamentPHP 5.7, Spatie Laravel Permission, Simple QrCode, and the PHPUnit testing framework. Vite, Tailwind CSS, Alpine.js, Axios, and the Laravel Vite plugin support the frontend development workflow. Git is suitable for tracking the source code and its changes, but the current application documentation does not provide evidence of a particular remote repository or branching strategy.

## 5.3 Programming Languages and Tools

The backend is written in PHP 8.2 or later and uses Laravel 12 as the main application framework. Laravel provides routing, authentication, database migrations, Eloquent ORM models, validation, password hashing, configuration, and the Artisan command-line interface. The application follows Laravel's model and migration conventions to represent assets, departments, locations, maintenance logs, audits, gate passes, users, and saved inventory reports.

FilamentPHP 5.7 provides the administrative panel used to manage the inventory. Filament resources define the forms, tables, filters, record actions, and authorization checks for assets, users, maintenance logs, audits, and gate passes. Filament pages provide the reports view, while the inventory overview widget presents live counts for devices, warranties, maintenance, decommissioned assets, locations, and departments. This approach allowed the system to provide a consistent administrative interface without building every table and form from the ground up.

MySQL is the intended relational database management system, with Laravel migrations defining the structure of the application tables. Eloquent models provide the relationships between users, assets, departments, locations, maintenance logs, audits, gate passes, and inventory reports. Spatie Laravel Permission supplies roles and permissions, while Simple QrCode generates QR codes for signed asset-information URLs. Tailwind CSS and Vite support the styling and frontend asset build process. The project also includes Laravel Breeze for authentication-related functionality and PHPUnit for automated testing.

## 5.4 System Modules Developed

The authentication and authorization module uses Laravel's authentication features together with Spatie Laravel Permission. Users have names, email addresses, hashed passwords, and optional email verification timestamps. The seeded permission set includes permissions for viewing, creating, editing, deleting, and condemning assets, viewing and managing maintenance, managing users, viewing reports, managing audits, and managing gate passes. The seeded roles are Administrator, Inventory Manager, Technician, Auditor, and Read Only. Resource and page methods use these permissions to restrict sensitive operations such as user administration, maintenance management, and access to reports.

The asset management module provides the main inventory record. It allows authorized users to create, view, edit, and delete assets and to record asset tags, serial numbers, MAC addresses, types, brands, technical specifications, purchase dates, warranty dates, departments, locations, assigned users, assignment dates, assignment notes, status, and decommissioning information. The implemented asset form uses active and decommissioned as its available lifecycle values. Database uniqueness constraints protect asset tags, serial numbers, and non-null MAC addresses from duplication.

The QR code module is implemented as an action in the asset table. When a user requests a QR code, the application creates a signed route for the asset information page and generates the QR code using the Simple QrCode package. The code is displayed in a Filament modal and is not stored as a permanent uploaded image. The application includes configuration for the base URL used when creating the signed route so that the generated link can be adjusted for the environment in which the system is deployed.

The maintenance module records repair work against active assets. Each maintenance log stores the asset, technician, issue summary, detailed description, work status, resolution time, and resolution notes. The available work statuses are pending, in progress, and resolved. The module preserves maintenance history as a separate set of records and does not automatically change the asset lifecycle status when a maintenance log is created or resolved.

The audit and gate pass modules provide operational accountability. An audit records the asset checked, verification result, auditor, checking time, and notes. The available audit results are found, missing, damaged, and wrong location. A gate pass records a unique pass number, the asset collected, an optional resolved maintenance record, the collector's details, release time, issuing user, and notes. These modules support physical verification and controlled collection of hardware without introducing a separate asset-assignment table.

The reports module calculates and displays inventory, maintenance, and warranty information. Users with the view reports permission can see asset distributions by type, department, and location, maintenance counts by status, warranty counts, and recently generated reports. The system allows users to save inventory summary, maintenance, and warranty reports with a title, notes, calculated JSON summary, generating user, and generation time. The current module does not export reports to PDF or Microsoft Excel.

## 5.5 Testing Strategy

Testing was performed through the automated Laravel test suite and through verification of the implemented application behavior. The existing tests use PHPUnit through Laravel's testing commands. Feature tests exercise HTTP and authentication workflows, while the unit test currently verifies a basic assertion. Several feature tests use the RefreshDatabase trait so that database state is isolated between tests.

The current automated coverage focuses on the authentication and user profile areas. The authentication tests verify that the login screen is available, valid credentials authenticate a user, invalid credentials are rejected, and users can log out. Other feature tests cover registration, email verification, password reset, password confirmation, password updates, profile updates, and account deletion. A basic application response test verifies that the root route returns a successful response. These tests provide evidence for the authentication and profile workflows, but they do not yet constitute complete automated coverage of asset, maintenance, audit, gate pass, QR code, report, or role-permission workflows.

Integration testing for the inventory modules should be expanded to verify the relationships and authorization rules used by the application. Suitable tests would create departments, locations, users, and assets, then verify that assets can be saved with valid relationships and cannot be saved with duplicate identifiers. Additional tests should verify maintenance status values, audit results, gate pass associations, report summaries, QR code actions, and access restrictions for each seeded role. Until those tests are added and executed, the results for these modules should be described as manual or implementation-level verification rather than as completed automated test coverage.

User acceptance testing should be carried out with representative NRZ users after the inventory workflows are stable. The proposed scenarios include registering an asset, assigning it to a department and user, viewing its QR code, recording a maintenance issue, resolving the issue, creating a gate pass, completing an audit, and generating a report. The current application does not contain a separate scanner workflow, so QR code testing should verify the generated signed URL and the asset information route rather than claim that technicians can scan and update records through a dedicated mobile scanning interface.

## 5.6 Test Data

The DatabaseSeeder provides repeatable demonstration data for local testing. It creates the permissions used by the application and configures five roles: Administrator, Inventory Manager, Technician, Auditor, and Read Only. It creates the departments IT, Finance, HR, Audit, Security, Traffic, and Marketing, together with the locations Bulawayo, Rutenga, Harare, and Lowveld. It also creates an administrator test account and demonstration users representing an inventory manager, a technician, and an auditor.

The seeder creates five sample assets covering a laptop, desktop, printer, server, and radio. The sample records contain asset tags, serial numbers, selected MAC addresses, brands, JSON specifications, purchase dates, warranty dates, departments, locations, assignment data, and lifecycle states. Four sample assets are active or in service for normal inventory scenarios, while the radio is decommissioned with a condemnation reason. The seeded records also include two maintenance logs, two audit records, and one gate pass so that repair, verification, and controlled collection workflows can be demonstrated locally.

The seeded data is intended for development and demonstration, not for production use. The sample passwords and fictional contact details should be replaced before deployment, and the seed records should not be interpreted as actual NRZ inventory. Its purpose is to provide consistent records for exercising the forms, relationships, dashboard statistics, reports, and permission-controlled navigation.

## 5.7 Test Results

The existing automated tests provide evidence that the authentication and profile workflows operate as expected under the test conditions. The tests verify successful rendering of authentication pages, valid and invalid login behavior, logout behavior, registration, password management, email verification, profile updates, and account deletion. The root response test also confirms that the application's initial route returns a successful response in the configured test environment.

The application source and seeder provide implementation-level evidence for the inventory workflows. The database models define the relationships between assets and their departments, locations, assigned users, maintenance logs, and audits. The resource forms define required fields and controlled status or result values, while the reports page calculates inventory, maintenance, and warranty summaries from database queries. The asset table contains the QR code action that generates a signed asset-information URL. These behaviors should be confirmed with dedicated feature tests before being presented as fully tested acceptance results.

No verified performance benchmark is included in the current test suite, so a two-second page-load target cannot be reported as an achieved result. Likewise, the available project evidence does not establish completed formal user acceptance testing with technicians, external-device scanning, security penetration testing, or high-volume load testing. These activities remain appropriate recommendations for the next testing stage.

## 5.8 Bug Fixes and Improvements

The implemented code includes several controls that improve reliability during normal operation. Asset and gate pass identifiers are protected by unique validation and database constraints. Relationship selectors and required fields reduce invalid foreign-key values and incomplete records. The reports page uses eager loading for related departments, locations, and generated report users when assembling the report view, which reduces unnecessary relationship queries in that page. The QR code action temporarily applies the configured base URL when generating a signed route and restores the previous URL configuration afterward, helping the generated link reflect the intended application address.

The current code does not provide sufficient evidence to claim that a documented N+1 query investigation, a completed mobile-table redesign, or a completed performance optimization was formally carried out during testing. The Filament interface supplies responsive administrative components, but no separate mobile scanner interface is implemented. Future improvements should therefore concentrate on dedicated inventory feature tests, authorization tests for each role, validation of QR links on the target network, report export requirements if needed, and usability testing on the devices used by NRZ personnel.

## 5.9 Chapter Summary

This chapter described how the NRZ Inventory System was implemented and tested. The system uses PHP 8.2 or later, Laravel 12, FilamentPHP 5.7, MySQL, Eloquent, Spatie Laravel Permission, Simple QrCode, Tailwind CSS, Vite, and PHPUnit. The completed modules cover authentication and authorization, asset management, QR code generation, maintenance, audits, gate passes, dashboard statistics, and saved inventory reports.

The chapter also documented the repeatable demonstration data supplied by the DatabaseSeeder and accurately described the current automated test coverage. Authentication and profile workflows have automated tests, while the inventory modules are implemented but require additional dedicated feature, authorization, acceptance, and performance tests before comprehensive results can be claimed. This distinction provides a reliable basis for further testing, deployment preparation, user training, and maintenance planning in the next stage of the project.
