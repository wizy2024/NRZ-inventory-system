# CHAPTER 6: IMPLEMENTATION AND POST-IMPLEMENTATION PLAN

## 6.1 Introduction

The implementation phase translates the completed Laravel and FilamentPHP design into a usable inventory management application and prepares the system for controlled organizational use. The NRZ Inventory System currently operates as a web-based administrative application with authentication, role and permission controls, asset management, maintenance records, audits, gate passes, QR code generation, dashboard statistics, and saved inventory reports. This chapter describes the activities required to move from local development and demonstration data toward a managed production installation. It also presents the training, data preparation, maintenance, user support, and technical documentation plans required for continued operation.

The current project is ready for further deployment preparation, but it should not be described as already deployed to a live NRZ production environment. Production configuration, infrastructure approval, data migration, user training, backup automation, and formal acceptance should be completed and documented before the system is declared operational. The post-implementation plan therefore combines the features already available in the application with the future activities required for a reliable rollout.

## 6.2 User Training Plan

User training will be organized according to the roles and permissions implemented in the system. Administrators will be trained to manage users, assign roles and permissions, maintain departments and locations, review system access, and coordinate backups and configuration changes with the IT team. Inventory Managers will be trained to register assets, maintain serial numbers and asset tags, assign assets to departments and users, record decommissioning information, view dashboard statistics, generate QR codes, issue gate passes, record audits, and create inventory, maintenance, and warranty reports.

Technicians will receive practical training on viewing assets, creating and updating maintenance logs, selecting the appropriate pending, in-progress, or resolved status, and recording resolution notes. Auditors will be trained to record the verification result of an asset as found, missing, damaged, or in the wrong location, together with the checking date and audit notes. Read Only users will be shown how to search and view permitted inventory and maintenance information without receiving permissions to alter records.

Training should use the seeded demonstration records or a separate training database so that staff can practise without affecting production data. The current system provides a QR code action that generates a signed asset-information link, but it does not contain a dedicated mobile scanning workflow. Training should therefore focus on the implemented QR display and asset-information route. Any future mobile or scanner-based workflow should be introduced only after it has been developed, tested, and approved. Attendance records, practical exercises, and a short user acceptance checklist should be retained as evidence that each role can complete its core tasks.

## 6.3 Conversion Plan

A phased conversion approach is recommended for moving from existing manual records to the NRZ Inventory System. The first phase should prepare the production environment, confirm the responsible system administrators, configure the database and application URL, and verify that authentication, roles, permissions, asset registration, maintenance, audit, gate pass, QR, and report workflows operate correctly. The second phase should introduce the system to a controlled pilot group or selected department while existing records are checked and corrected.

During the pilot, a short parallel operating period may be used where organizational policy requires continuity with existing paper or spreadsheet records. The parallel period should have a defined start date, responsible users, reconciliation procedure, and end date. It should not continue indefinitely because duplicate entry can create conflicting information. Once the pilot records have been reconciled and users have demonstrated proficiency, the system can become the official source for new asset movements and operational records. Additional departments and locations can then be added in stages after each stage has been reviewed.

The present project includes seeded locations such as Harare, Bulawayo, Rutenga, and Lowveld, but these are demonstration records and do not by themselves confirm the final rollout order. The actual pilot location, participating departments, network arrangements, and cutover date should be agreed with NRZ management and the IT support team before deployment.

## 6.4 Data Migration Plan

Data migration should begin with an inventory of the existing spreadsheets, registers, paper forms, and other records that are approved as sources. The records should be cleansed before import by removing duplicates, standardizing department and location names, confirming asset tags and serial numbers, and identifying assets with missing or uncertain information. Each source record should be assigned a migration status so that unresolved records can be reviewed rather than silently inserted as complete information.

The cleaned data should be mapped to the fields in the current assets, departments, locations, and users tables. Asset tags and serial numbers should be checked for uniqueness, while each asset should be linked to a valid department and location. Assignment information should be added only when the assigned user has a corresponding account. Existing maintenance, audit, and gate pass information should be migrated separately where the source data contains enough detail to populate those records reliably.

The current application does not include a completed CSV import feature or a Filament bulk-import workflow. Data migration should therefore use a reviewed Laravel command, a controlled database script, or carefully prepared administrative entry until an import feature is implemented. The migration process should be tested first against a copy of the database and should produce an exception list for invalid rows. After import, the team should reconcile record counts and verify a documented sample of assets, departments, locations, assignments, warranties, and statuses. A ten percent verification sample may be adopted as a project control, but it is a proposed procedure rather than a completed result of the current system.

## 6.5 Maintenance Plan

Application maintenance will include monitoring Laravel, FilamentPHP, PHP, Composer packages, Node.js packages, and frontend dependencies for security updates and compatibility changes. Updates should first be applied in a test or staging environment, followed by the automated test suite and a focused review of login, authorization, asset, maintenance, audit, gate pass, QR, and report workflows. Only approved updates should be promoted to production, and the version and date of each update should be recorded.

Database maintenance should include checking storage growth, reviewing query performance as inventory records increase, and confirming that foreign-key relationships and unique constraints remain intact. The application currently stores structured specifications and report summaries in the database and uses the local filesystem disk for file storage. Since the current system does not provide document uploads, backup planning should focus first on the database, application source, environment configuration, and any generated or operational files that are introduced during deployment.

Backups are a required future operational control and have not been automated by the current project files. Before go-live, the IT team should define a schedule for database backups, retention periods, encryption, off-site storage, and restoration tests. A practical policy could include frequent database backups and periodic full backups, but the exact daily or weekly schedule should be approved according to NRZ infrastructure and data-retention requirements. A backup should only be considered effective after a restoration test has demonstrated that the application can be recovered.

Operational maintenance should also include reviewing user accounts and permissions, removing inactive access, checking application logs, verifying the configured application and QR base URLs, and confirming that the server clock and database time zone are correct. Any incident affecting data accuracy, access control, availability, or QR links should be recorded with its cause, corrective action, and resolution date.

## 6.6 User Manual

A user manual will be prepared for the staff who operate the system. It should explain how to open the application, authenticate, navigate the Filament sidebar, search for an asset, create and update an asset record, assign an asset, view a QR code, create a maintenance log, complete an audit, issue a gate pass, and generate a report. The manual should use the actual labels and workflows shown in the current application, including the distinction between asset lifecycle statuses and maintenance work statuses.

The manual should also explain the information required for asset registration, the importance of unique asset tags and serial numbers, the handling of decommissioned assets, and the meaning of audit results. Troubleshooting guidance should cover invalid credentials, missing permissions, unavailable related departments or locations, invalid or inaccessible QR links, and what to do when a record contains incorrect information. Because the current system does not implement a dedicated scanner workflow or document-upload feature, the manual should not instruct users to perform those actions until they are added and tested.

The final manual should include screenshots from the approved deployment environment and should be reviewed by an Inventory Manager and an Administrator before distribution. It can be supplied as an appendix to the final project documentation and maintained as a versioned document so that changes to the interface and permissions are reflected in later editions.

## 6.7 Technical Documentation

Technical documentation will be handed over to the NRZ IT administration team to support independent operation of the system. It should describe the Laravel application structure, PHP and Node.js requirements, Composer and npm installation, environment variables, database configuration, application URL configuration, QR base URL configuration, storage permissions, web-server setup, and SSL requirements. The deployment documentation should specify that debug mode must be disabled in production and that application secrets must not be committed to source control.

The technical handover should include the database migrations, the seeded roles and permissions, the principal Eloquent relationships, and the procedures for running migrations, clearing configuration and application caches, building frontend assets, and executing the automated tests. Typical maintenance commands include `php artisan migrate`, `php artisan optimize:clear`, `npm run build`, and `php artisan test`, but commands should be executed according to the approved deployment procedure and database backup policy.

The handover should also include the entity relationship diagram, permission matrix, data migration mapping, backup and restoration procedure, incident contacts, and release history. The current project does not include a production deployment script, automated backup script, CSV import command, or completed user manual, so these deliverables should be marked as future implementation or operational tasks rather than presented as existing system capabilities.

## 6.8 Chapter Summary

This chapter presented the implementation and post-implementation plan for the NRZ Inventory System. It confirmed that the current Laravel and FilamentPHP application provides the core workflows for authentication, role-based access, asset records, maintenance, audits, gate passes, QR code display, dashboard monitoring, and saved reports. It also identified the seeded data and local configuration that support development and demonstration.

The proposed rollout consists of controlled deployment preparation, role-based training, phased conversion, verified data cleansing and migration, and formal user acceptance before production use. Long-term operation will require dependency updates, access reviews, database and application backups, restoration testing, monitoring, user documentation, and technical handover. CSV import, mobile scanning, production deployment, automated backups, and other extended capabilities remain future plans and should be implemented and tested before being described as completed features. These actions provide a realistic path from the current development system to a maintainable NRZ operational service.
